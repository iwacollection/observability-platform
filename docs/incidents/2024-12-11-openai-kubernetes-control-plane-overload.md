# 2024-12-11 OpenAI Kubernetes 控制面过载事故复盘

> **复盘范围**：只记录 OpenAI 官方公开复盘确认的事实，以及基于 Kubernetes 官方机制提出的整改建议。本文不把未经官方确认的 CFS、etcd、CNI 或具体 API 请求实现写成事故根因。
>
> **事故日期**：2024-12-11  
> **主要故障域**：大型 Kubernetes 集群的 API Server / 控制面，以及依赖 Kubernetes DNS 服务发现的业务  
> **官方复盘**：[OpenAI Status — API, ChatGPT & Sora Facing Issues](https://status.openai.com/incidents/ctrsv3lwd797/write-up)

## 1. 事故摘要

2024 年 12 月 11 日，OpenAI 在全球 Kubernetes 集群推广一项新的遥测服务。该服务的配置导致集群中的**每个节点都执行高成本 Kubernetes API 操作，而且单次操作成本会随集群规模增长**。数千个节点同时执行这些操作后，大型集群的 Kubernetes API Server 被压垮，多数大型集群的控制面受到影响。

Kubernetes 数据面在一定程度上可以独立于控制面运行，但集群内部服务发现依赖 DNS。节点 DNS 缓存暂时保留了可用记录，使故障没有立即完全显现；缓存约在随后 20 分钟内逐渐过期后，业务开始出现 DNS 服务发现失败，DNS 请求增加又进一步增加了恢复压力。

**核心结论：这是一次由遥测服务配置和请求模式引起的 Kubernetes API 负载过载事故。** 事故不是因为某个未证实的内核、网络或存储故障；真正需要整改的是采集器请求设计、发布规模验证、控制面保护、DNS/数据面依赖以及紧急恢复通道。

## 2. 业务影响

官方公布的影响窗口为 **15:16–19:38 PST**。期间 OpenAI 服务出现明显降级或完全不可用。

| 产品 | 明显恢复 | 完全恢复 |
|---|---:|---:|
| ChatGPT | 17:45 PST | 19:01 PST |
| API | 17:36 PST | 19:38 PST |
| Sora | — | 19:01 PST |

不同产品的恢复时间不同。控制面恢复、流量迁移和产品端恢复不是同一个时间点。

## 4. 根因分析

### 4.1 直接根因：遥测服务产生了随集群规模放大的 API 负载

官方确认的事实：

1. 新服务用于采集 Kubernetes 控制面指标，部署范围覆盖集群节点。
2. 新服务配置导致每个节点执行高成本 Kubernetes API 操作。
3. 这些操作的成本随集群规模增长。
4. 数千个节点同时执行操作后，大型集群 API Server 过载，多数大型集群的 Kubernetes 控制面受到影响。

可将问题抽象为：

`集群总 API 负载 ≈ 节点实例数 × 单个实例产生的 API 工作量`

当单个实例的工作量也随集群规模增长时，扩大集群不仅增加节点数量，也会提高每个节点触发的 API 工作成本，最终形成明显的规模放大效应。

**官方没有公开具体 API 动词、资源类型、请求频率、客户端实现或代码路径。** 因此本文不把“每个节点执行全量 LIST”“没有使用 Informer”“绕过 Watch Cache”等具体实现写成已证实事实。这些可以作为代码审计时要验证的假设，但不能冒充 RCA 结论。

### 4.2 故障扩散：DNS 缓存延迟暴露服务发现问题

官方确认：

- Kubernetes 数据面可以在一定程度上独立于控制面运行；
- DNS 服务发现依赖 Kubernetes 控制面；
- 节点 DNS 缓存暂时提供了仍可工作的旧记录；
- 缓存记录在随后约 20 分钟内逐渐过期，业务开始因 DNS 解析失败受到影响；
- 缓存失效后，DNS 请求量增加，进一步增加了控制面恢复压力。

因此故障链为：

```text
遥测服务大范围部署
        ↓
每个节点执行高成本 Kubernetes API 操作
        ↓
API Server 负载随集群规模放大
        ↓
大型集群 Kubernetes 控制面过载
        ↓
DNS 服务发现无法正常维持 / 更新
        ↓
节点已有 DNS 缓存暂时掩盖故障
        ↓
缓存逐渐过期，DNS 查询和失败增加
        ↓
依赖服务发现的业务受到影响
```

这里的重点是：DNS 缓存只延迟了故障暴露，并没有消除对控制面的依赖。

### 4.3 促成因素：发布验证没有覆盖控制面负载

官方复盘指出，变更在 Staging 集群测试时没有发现问题，问题主要在超过一定规模的集群中显现。

发布前重点检查的是新遥测服务自身的 CPU、内存，并按集群调整了资源请求；但没有采取措施评估它对 Kubernetes API Server 的负载影响。发布流程监控了服务健康，却缺少充分的集群健康监控。

因此，测试通过不能证明生产安全：测试环境没有覆盖足够大的集群规模，也没有把 API Server 负载作为发布门禁。

### 4.4 恢复困难：管理操作依赖已经过载的控制面

通常回滚问题服务需要访问 Kubernetes API Server 删除或修改资源。但本次事故中，API Server 正是过载对象，工程师无法正常访问控制面来移除问题服务。

这形成了管理面锁定效应（Locked-out Effect）：

```text
需要移除问题遥测服务
        ↓
需要访问 Kubernetes API Server
        ↓
API Server 已经严重过载
        ↓
无法及时执行常规回滚
        ↓
必须先通过其他手段恢复控制面访问
```

这不是最初的触发原因，但显著延长了恢复时间。

### 4.5 恢复阶段的次生问题

官方还说明，部分集群在控制面恢复后，许多服务同时尝试下载资源，导致资源限制被触发，仍需额外人工处理。

这属于恢复阶段的并发启动 / 资源下载冲击，不是最初的 API Server 过载根因，但应纳入恢复预案。

## 5. 根因边界：哪些不应写成此次事故根因

为避免把推测写成事实，本次 RCA 不将以下项目列为根因：

| 项目 | 本次复盘的处理方式 |
|---|---|
| CFS CPU throttling | 官方未确认；没有节流数据就不能归因为 CFS |
| etcd 性能或磁盘瓶颈 | 官方未确认是直接根因；不在根因链中展开 |
| CNI 网络故障 | 官方未确认；不作为故障触发点或根因 |
| CoreDNS 重启 / OOM | 官方没有披露此类事实；只描述已确认的 DNS 依赖和缓存失效过程 |
| 全量 LIST、缺少 Informer、绕过 Watch Cache | 具体采集实现未公开；只作为后续代码审计假设，不写成事故事实 |

这些组件可以在未来的独立性能排障中根据证据分析，但不能为了“讲得深入”而把没有证据的环节添加进这次事故链。

## 6. 止血与恢复过程

官方确认，团队并行推进了三项措施：

1. **缩小集群规模**：降低集群整体 Kubernetes API 负载。
2. **阻断到 Kubernetes 管理 API 的网络访问**：阻止新的高成本请求继续进入，为 API Server 恢复争取空间。
3. **扩充 Kubernetes API Server 处理能力**：提高可处理请求的能力，恢复执行修复操作的窗口。

通过并行执行这些措施，团队最终恢复了足够的控制能力，移除了问题遥测服务。随后，在可行的情况下，将业务流量迁移到健康集群。控制面恢复后，部分集群又因大量服务同时下载资源而出现资源限制，需要进一步人工处理。

推荐将恢复动作整理成可执行 Runbook：

| 阶段 | 操作目标 | 完成验证 |
|---|---|---|
| 止血 | 暂停遥测服务继续推广；通过预先准备的网络控制手段限制其 API 访问 | API 请求压力停止继续增长 |
| 恢复控制面 | 降低集群负载、恢复 API Server 服务能力 | API 请求成功率和延迟回到可操作范围 |
| 移除故障源 | 删除或停用问题遥测配置与工作负载 | 不再产生异常 API 请求 |
| 恢复服务发现 | 验证 DNS 和关键 Service 解析 | 核心服务间 DNS 查询成功 |
| 恢复业务 | 分批恢复流量、服务和资源下载 | 业务成功率、延迟和错误率恢复 |
| 稳定观察 | 观察 API、DNS、集群和业务指标 | 指标持续稳定，无二次请求风暴 |

表格中的验证项是建议的 Runbook 标准，不代表官方披露了每项具体执行记录。

## 7. 后续优化方案

整改按“先消除负载源，再保护控制面，最后提高故障隔离和恢复能力”的顺序实施。

### P0：重构遥测采集器，避免重复消耗控制面

**目标：采集系统不能因为扩大部署规模而同比例或超线性地放大控制面负载。**

- 节点级 Agent 只负责本机指标，例如本机 CPU、内存、磁盘、网络和容器运行数据；能从本地数据源获得的指标，不要为此查询集群级 API。
- Kubernetes 集群资源由集群级 Collector 统一维护，优先使用 client-go SharedInformer 的 LIST + WATCH + 本地缓存模式，避免多个采集模块重复读取相同资源。
- 按需订阅资源类型、Namespace 和节点范围，避免读取并处理不需要的对象。
- 对采集器的 API QPS、Burst、最大并发请求数设置明确上限。
- 断线、缓存失效或 `410 Gone` 后重新同步时，使用退避和随机抖动，避免大量实例同时重新 LIST。
- 将缓存同步失败、WATCH 重连、重 LIST、请求限流和采集数据过期显式暴露为指标。

**架构示意：**

```text
Node Agent（每节点）
  ├── 本机 CPU / 内存 / 磁盘 / 网络
  └── 本地容器运行指标
              │
              ▼
Cluster Collector（集群级）
  ├── 受控 LIST / WATCH
  ├── 共享 Informer / 本地索引
  ├── API 请求预算
  └── 缓存与增量状态
              │
              ▼
Metrics Backend / Alerting
```

注意：SharedInformer 共享的是同一进程内的缓存和 Watch。若每个节点上的独立 Agent 各自创建一套全量 Informer，并不会自动变成集群级共享缓存。因此需要明确集群级采集器、分片或其他共享状态设计。

### P1：发布流程增加集群健康门禁

**目标：新服务自身健康不等于集群健康。**

- 先部署到代表性 Canary 集群，必须覆盖接近生产最大规模的节点数、Pod 数量和资源变化量。
- 按小批次逐步扩展范围；每个批次观察集群健康后再继续。
- 观察窗口必须覆盖已知 DNS 缓存延迟窗口，不能在缓存仍掩盖故障时继续快速推广。
- 发布门禁同时检查服务自身和集群控制面指标。
- 发现 API 请求量、延迟、排队或拒绝异常时自动暂停推广；达到预设回滚条件时停止问题服务。
- 回滚动作不能只依赖被发布组件所在的 Kubernetes API 路径，应预先验证紧急隔离手段。

发布门禁至少包括：

| 维度 | 门禁信号 |
|---|---|
| 遥测服务 | API 请求速率、并发、请求错误、重试、缓存同步时间 |
| API Server | 请求速率、按 verb/resource/status 分类的请求延迟和错误率、in-flight 请求 |
| APF | 排队长度、等待时间、拒绝数、PriorityLevel Seat 利用率 |
| DNS | 查询成功率、SERVFAIL、超时、查询延迟和请求量 |
| 集群健康 | 节点 Ready、核心控制器同步、关键业务探针 |
| 业务 | 关键服务成功率和延迟 |

阈值不要照搬固定数字。应以生产基线、SLO、压测得到的安全容量和预留余量设定。

### P2：使用 APF 保护关键控制面流量

**目标：低优先级遥测请求不能挤占节点心跳、核心控制器等关键请求的处理能力。**

- 为遥测服务使用独立 ServiceAccount。
- 使用 FlowSchema 将该身份的请求识别出来。
- 将其分配到受限的 PriorityLevelConfiguration，控制其并发席位和排队容量。
- 确保节点健康更新、关键控制器和 Leader Election 等流量拥有合理的优先级和容量。
- 验证规则匹配结果，避免遥测服务意外匹配到高优先级规则。

APF 是控制面过载保护，不是采集器架构优化的替代品。昂贵请求即使被降级，也仍会消耗资源。

### P3：降低业务对控制面的关键依赖

**目标：控制面短时不可用时，已经运行的关键业务能够继续工作更长时间。**

- 梳理业务服务发现是否必须依赖实时 Kubernetes API 状态。
- 对关键服务评估更稳健的服务发现和缓存策略。
- 验证 CoreDNS 在 API Server 不可用、连接恢复、缓存未同步和重启后的行为。
- 合理部署 DNS 副本，避免单一节点故障导致 DNS 服务整体不可用。
- 明确 DNS 缓存 TTL 与业务容错之间的关系；不能单纯无限延长 TTL 来掩盖控制面问题。
- 将 DNS 查询成功率和服务间解析探针纳入发布门禁。

CoreDNS Kubernetes 插件官方文档说明，它会同步 Kubernetes 对象 Watch；未完成同步时，相关 Kubernetes 记录查询可能返回 SERVFAIL。插件也支持配置 API QPS、Burst 和最大并发请求数，可用于限制其 API 请求压力。

### P4：建立独立的 Break-glass 控制面访问

**目标：当数据面或某个控制器压垮 API Server 时，运维仍能执行隔离和恢复。**

- 预先设计独立于常规集群工作负载流量的紧急管理路径。
- 由受控管理网络和最小权限身份访问 API Server。
- 保留紧急隔离遥测服务 API 访问的网络策略、ACL 或平台侧操作能力。
- 对紧急凭据、操作记录、审批和审计进行管理。
- 定期演练：在常规 `kubectl` 操作不可用时，仍能限制请求源并恢复管理能力。

Break-glass 不是绕过安全审批的永久后门，必须受访问控制、审计和演练约束。

### P5：抑制恢复阶段的第二次资源冲击

**目标：恢复控制面后，不让所有工作负载同时重新初始化。**

- 服务恢复分批进行，控制并发启动数量。
- 对镜像、模型或其他启动资源下载设置并发和速率限制。
- 对启动依赖资源采用合理缓存和预热策略。
- 对控制器重连、WATCH 重建、客户端重试和业务启动设置退避及随机抖动。
- 定期演练集群批量恢复或替换，验证恢复时间与依赖顺序。

## 8. 监控与告警设计

重点不是“多加指标”，而是能尽早发现采集器对 API Server 的影响。

| 监控对象 | 建议监控内容 | 目的 |
|---|---|---|
| 遥测 Collector | API QPS、Burst、并发、请求错误、LIST 次数、WATCH 重连、重同步次数、缓存同步时间 | 识别采集器是否制造请求压力 |
| API Server | 按 verb、resource、身份、状态码统计请求量与延迟；请求并发和错误率 | 找到请求来源与控制面饱和趋势 |
| APF | 队列长度、等待时间、拒绝请求、Seat 利用率 | 发现优先级隔离是否生效 |
| CoreDNS | DNS QPS、查询延迟、SERVFAIL、超时、API 客户端请求指标 | 发现服务发现异常与 API 依赖问题 |
| 集群 / 业务 | Node Ready、核心控制器状态、关键服务 DNS 探针、业务成功率和延迟 | 识别真实用户影响 |

建议重点关注的 APF 指标：

- `apiserver_flowcontrol_rejected_requests_total`
- `apiserver_flowcontrol_current_inqueue_requests`
- `apiserver_flowcontrol_request_wait_duration_seconds`
- `apiserver_flowcontrol_priority_level_seat_utilization`

CoreDNS Kubernetes 插件还提供 API 客户端请求延迟、客户端限流等待时间和请求状态码等指标，可用于定位 DNS 组件自身对 API Server 的请求情况。

## 9. 整改验收标准

整改不能以“配置已提交”作为完成标准，必须通过压测、故障注入和恢复演练验收。

| 验收项 | 测试方法 | 通过标准 |
|---|---|---|
| 采集器负载可控 | 在代表性大规模集群同时启动采集器 | API 请求量和并发不突破批准的请求预算 |
| 资源采集效率 | 对比改造前后的 API 请求量、返回对象量和采集延迟 | 不再由每个节点重复执行不必要的集群级资源读取 |
| 断线恢复 | 中断 WATCH、模拟 ResourceVersion 过期 | 重新同步有退避和抖动，不出现集中重试风暴 |
| 控制面保护 | 对遥测身份施加高负载 | APF 将其限制在分配的容量内，关键请求仍满足 SLO |
| 发布保护 | 在 Canary 集群注入异常配置 | 集群健康门禁暂停推广，回滚/隔离流程可执行 |
| DNS 容错 | 暂时阻断 CoreDNS 到 API Server 的连接并恢复 | DNS 行为符合设计，关键服务探针可验证恢复 |
| 紧急访问 | 模拟常规 API 操作不可用 | Break-glass 路径可隔离请求源并恢复管理操作 |
| 恢复能力 | 模拟批量服务重启和资源下载 | 并发受控，不产生第二次资源冲击 |

所有阈值应在目标集群上基于 SLO 和压测确定，记录基线、目标值、测试数据与结果。未执行的测试不得标记为已验收。

## 10. 整改优先级

| 优先级 | 工作项 | 交付物 |
|---|---|---|
| P0 | 审计遥测服务所有 Kubernetes API 调用 | API 调用清单、资源范围、频率、并发和响应规模 |
| P0 | 重构重复采集路径，建立集群级缓存和请求预算 | 采集架构图、代码变更、压测数据 |
| P0 | 发布门禁增加 API Server / DNS / 集群健康信号 | Canary 策略、暂停条件、回滚条件 |
| P1 | 为遥测身份配置 APF 隔离 | FlowSchema、PriorityLevelConfiguration、压测结果 |
| P1 | 建立 Break-glass 控制面访问 | 操作手册、访问审计、演练记录 |
| P1 | DNS 和数据面依赖解耦评估 | 依赖清单、容错设计、故障注入报告 |
| P2 | 建立恢复阶段资源下载限流与分批启动 | 恢复 Runbook、恢复演练结果 |
| P2 | 定期开展大规模集群和控制面故障注入 | 测试报告、问题清单、整改跟踪 |

## 11. 复盘结论

这次事故的主要问题不是 Kubernetes 单组件“性能差”，而是遥测服务在大规模集群中产生了不可控的 API 负载，并且发布验证没有把控制面健康纳入门禁。DNS 缓存延迟暴露了服务发现故障，而常规回滚又依赖已经过载的 API Server，导致恢复被进一步拖慢。

后续优化必须形成闭环：

```text
采集器请求治理
    ↓
大规模集群验证
    ↓
分阶段发布 + 集群健康门禁
    ↓
APF 控制面流量隔离
    ↓
DNS / 数据面依赖降级
    ↓
Break-glass 紧急访问
    ↓
分批恢复 + 故障注入演练
```

**最终原则：观测系统不能成为被观测系统的故障源；发布验证必须覆盖控制面健康；恢复手段不能完全依赖已经故障的控制面。**
